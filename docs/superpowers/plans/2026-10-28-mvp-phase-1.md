# MVP Phase 1 (Local) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the to-do app's first version so it runs locally: magic-link sign-in, a "Next up" home screen with suggestions based on simple rules, quick add that understands plain text, lists and tasks, in the Daylight look.

**Architecture:**
- A Next.js 16 App Router app on the existing Supabase schema.
- Pure, unit-tested modules in `lib/` handle dates, quick-add parsing, Next up grouping and suggestions.
- Server Components read through `server-only` data modules, and thin Server Actions write.
- UI is stock shadcn components, styled only through theme tokens in `app/globals.css`.
- The database gains three small additions:
  - a "has time" flag on due dates
  - a starter list for every new user
  - a table that stores dismissed suggestions

**Tech Stack:** Next.js 16.3.6, React 19.2, Tailwind 4, shadcn/ui (Radix, lucide-react, sonner), `@supabase/ssr` 0.12, `date-fns` + `@date-fns/tz`, Vitest, Supabase CLI 2.120 with pgTAP, pnpm.

**Spec:** `docs/superpowers/specs/2026-10-28-mvp-product-design.md`. This plan covers Phase 1 only. Phase 2 (deployment) gets its own plan.

## Global Constraints
- Who commits: helpers never stage or commit. A "Commit" step means the orchestrator commits, and only inside a Docker Sandbox VM as the agent account. Run on the user's Mac, the orchestrator hands the user the command and message instead.

- Use pnpm for everything. Never npm or npx. Only the orchestrator runs `pnpm add`.
- Ownership: `backend` writes `supabase/**`, `lib/database.types.ts` and `docs/contracts/db-contract.md`. `frontend` writes `app/**`, `components/**`, the rest of `lib/**`, `proxy.ts` and `public/**`. The orchestrator owns `package.json`, the lockfile, configs, `scripts/**` and `.claude/**`. Nobody edits `.env*`.
- The schema lands before the frontend work that depends on it: Task 2 merges before Tasks 5–8.
- Never decide by status name or id, only by `behavior`. The one allowed lookup is the built-in status with a given behaviour (`owner_id is null and behavior = 'completed'`).
  - Open: behaviour not in (`completed`, `cancelled`).
  - Active: `in_progress`, `blocked`, `in_review`.
- The database enforces the rules. Map its errors using the contract's error catalogue. Client-side checks are only a convenience.
- Read the matching guide in `node_modules/next/dist/docs/` before using any Next.js API. Middleware is now `proxy.ts`. Cite the guide in the report; the orchestrator puts it in the commit message.
- Use only `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY`, with the `@supabase/ssr` clients in `@/lib/supabase`. Lint enforces this.
- The frontend agent can't start Supabase (`pnpm supabase` isn't on its allowlist). Before Tasks 5–8:
  - The orchestrator runs `pnpm supabase start`.
  - The owner puts the local API URL and anon key in `.env.local` as `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY`.
- The login form never creates accounts: call `signInWithOtp` with `shouldCreateUser: false`.
- Priority is stored as a smallint: High = 3, Medium = 2, Low = 1, none = null.
- Suggestion thresholds, copied from the spec:
  - Stale: 14 days untouched.
  - "Not now" hides a suggestion for 7 days.
  - Rhythm: 3 or more completions of the same title.
  - Show at most 3 suggestions.
- Copy, exactly as written:
  - Next up header: "N things need you" (use "1 thing needs you" for one, and "Nothing needs you right now" when empty)
  - Group headings: "Overdue", "Today", "Keep it moving", "Suggested from your history"
  - Suggestion buttons: "Add for today" and "Not now" (rhythm); "Do today", "Move to Backlog" and "Not now" (stale)
- Look: Daylight. Airy, cool-grey surfaces, a coral accent, Bricolage Grotesque for display text and Figtree for body text. Dark mode follows the device setting through `prefers-color-scheme`, with no toggle. Reference: option A in https://claude.ai/code/artifact/8f3771c0-aa22-4b62-83ca-8455de378ca5.

## Review Focus

1. **Quick add with no title left.** Typing `!high #home` should make the app say "Add a title". It should never send an empty title to the database. Pinned in Task 3 (the parser returns `title: ""`) and Task 7 (the Add button is disabled).
2. **Words that look like dates.** `Read 1984`, `call may about rent` and `buy 3 apples` must keep their whole title and get no due date. Pinned in Task 3.
3. **The day boundary in the user's time zone.** In Los Angeles, a task due at 11pm today is still "Today" at 8pm, even though it's already tomorrow in UTC. Pinned in Task 4.
4. **List names with spaces or different case.** `#side-project`, `#SideProject` and `#sideproject` all match the list "Side project". `#nope` falls back to the starter list, and its chip says so. Pinned in Task 3.
5. **Ticking a task twice, or undoing after it has gone.** Completing an already-completed task changes nothing. Undo puts the task back in the exact status it was in before. Pinned in Task 7's `completeTask` / `undoComplete` contract and its manual check.

### Task 3: Dates and quick-add parsing (frontend, can run in parallel with Task 2)

**Files:**
- Create: `lib/time/zoned.ts`, `lib/time/zoned.test.ts`
- Create: `lib/quick-add/parse.ts`, `lib/quick-add/parse.test.ts`

**Interfaces:**
- Produces, in `lib/time/zoned.ts`, all built on `@date-fns/tz`'s `TZDate`:
  - `type LocalDate = string`, an ISO `YYYY-MM-DD`
  - `todayIn(timeZone: string, now: Date): LocalDate`
  - `localDayOf(iso: string, timeZone: string): LocalDate`
  - `toDueAt(date: LocalDate, time: string | null, timeZone: string): string`. Returns an ISO instant. `time` is `HH:mm`. A date-only due is stored as 12:00 local on that day.
  - `daysBetween(a: LocalDate, b: LocalDate): number`
- Produces, in `lib/quick-add/parse.ts`:
  ```ts
  export type ListRef = { id: string; name: string };
  export type ParsedQuickAdd = {
    title: string;                       // trimmed; "" if only tokens were typed
    due: { date: LocalDate; time: string | null } | null;
    priority: 1 | 2 | 3 | null;
    list: ListRef | null;                // matched list
    unmatchedList: string | null;        // the raw "#token" text when no list matched
  };
  export function parseQuickAdd(text: string, lists: ListRef[], today: LocalDate): ParsedQuickAdd;
  ```
- **Grammar.** Write a small parser for this; don't use a general date library. Matching ignores case. Each recognised token is removed from the title. When there are several date expressions, the last one wins.
  - **Priority:** `!high`, `!h` → 3; `!med`, `!medium`, `!m` → 2; `!low`, `!l` → 1.
  - **List:** `#token` matches the list whose name, lowercased with spaces, `-` and `_` removed, equals the token treated the same way.
  - **Dates:**
    - `today`, `tod`, `tomorrow`, `tmr`
    - weekday names, full or 3-letter. A weekday equal to today means today; otherwise it's the next occurrence.
    - `next week`, which means next Monday
    - `in N days`
    - month and day, as `nov 3` or `3 nov`. A month and day already past this year rolls to next year.
  - **Times:** `5pm`, `5:30pm`, `17:00`, optionally after `at`. Valid only when a date is also present, or on its own, which then means today.
  - **Never dates:** a bare month name, a bare number, and a 4-digit year.

### Task 4: Next up grouping and suggestions (frontend, can run in parallel with Task 2)

**Files:**
- Create: `lib/next-up/types.ts`, `lib/next-up/group.ts`, `lib/next-up/group.test.ts`, `lib/next-up/suggestions.ts`, `lib/next-up/suggestions.test.ts`

**Interfaces:**
- Consumes: `todayIn`, `localDayOf` and `daysBetween` from Task 3.
- Produces:
  ```ts
  // types.ts
  import type { Database } from "@/lib/database.types";
  export type Behavior = Database["public"]["Enums"]["status_behavior"];
  export type NextUpTask = {
    id: string; title: string; listId: string; listName: string;
    priority: 1 | 2 | 3 | null; dueAt: string | null; dueHasTime: boolean;
    statusId: string; statusLabel: string; behavior: Behavior;
    statusChangedAt: string; updatedAt: string; blockedReason: string | null;
  };
  export type CompletedTask = { title: string; listId: string; completedAt: string };
  export type Dismissal = { key: string; until: string };
  export type Suggestion =
    | { kind: "rhythm"; key: string; title: string; listId: string; reason: string }
    | { kind: "stale"; key: string; taskId: string; title: string; reason: string };
  // group.ts
  export function groupNextUp(tasks: NextUpTask[], now: Date, timeZone: string):
    { overdue: NextUpTask[]; today: NextUpTask[]; moving: NextUpTask[] };
  // suggestions.ts
  export function computeSuggestions(
    input: { open: NextUpTask[]; completed: CompletedTask[]; dismissals: Dismissal[] },
    now: Date, timeZone: string): Suggestion[];
  export function normalizeTitle(title: string): string; // lowercase, trim, collapse spaces
  ```
- **Grouping rules.** Only open tasks are grouped. A task appears in at most one group, checked in this order:
  - **Overdue:** the local due day is before today. Sorted oldest first.
  - **Today:** the local due day is today. Timed tasks are sorted by time, then date-only tasks.
  - **Keep it moving:** the behaviour is active and the task has no due date, or its due date is after today. Sorted by `statusChangedAt`, oldest first.
- **Rhythm rule:**
  - Group the completed tasks by `normalizeTitle`, keeping groups with 3 or more.
  - Work out the gaps in days between consecutive completions, and take their median *m*.
  - The rhythm is regular when every gap is within 0.5·*m* to 1.5·*m*.
  - The task is due again when the days since the last completion are at least 0.9·*m*, and no open task has the same normalized title.
  - `listId` is the list of the most recent completion.
  - Reason: `You add this about every {span}. Last time was {MMM d}.`, where span is "N days" below 14, "N weeks" below 60, and otherwise "N months" (*m*/30, rounded).
  - Key: `rhythm:{normalizedTitle}`.
- **Stale rule:**
  - The behaviour is `todo` or `backlog`, `dueAt` is null, and the task hasn't been updated for 14 or more days.
  - Reason: `In {statusLabel} for {N} days without a date.`
  - Key: `stale:{taskId}`.
- **Order and limits:** rhythm suggestions first (most overdue first), then stale ones (oldest first). Drop any suggestion with an active dismissal (`until > now`). Return at most 3.
